### A2 — Row-count normalisation: S1 vs S2–3 insight data

**What:** Session 1 captured `insight_generate_requested` + `insight_generate_completed` timeline events (2 rows per generation). Sessions 2–3 lost this instrumentation and fall back to reading the `.json` export `insights` array (1 row per insight). Raw row counts in `insight_generations.csv` are not directly comparable cross-session.

**Rule:** For S1 Sam solo and S1 Group AI_ON, count only `event_name = insight_generate_requested` rows. For all other contexts, count rows directly. The `data_source` column (`timeline_event` vs `export_fallback`) is the discriminating field.

**Cannot be fixed in the script** without introducing a derived column or a separate summary view. Apply the normalisation manually when building cross-session tables.

### A3 — `script6` undercounts context engagement

**What:** `script6_session_metrics.py` reports `context_saves` (i.e., `task_context_saved` events only). It does not count `draft_context_promoted` events. Any participant who used the promote pathway instead of or in addition to the panel save will appear under-engaged.

**Affected most:** Aung (S3) — 21 promotes in solo, 8 in group AI_ON, 4 in AI_LIGHT, against only 1 formal save. His script6 context_saves value of 1 severely understates his actual context activity.

**Rule:** For full context engagement figures, always use `output/context_events.csv` (generated by `script4_context_events.py`), which captures both pathways as of 2026-03-29. Break down by `event_name` to distinguish:
- `task_context_saved` — explicit panel save
- `draft_context_promoted` — promote-from-reply/insight, no panel open required
- `task_context_panel_toggled` — panel open/close interactions (informational)

### C2 — `draft_context_promoted` in AI_LIGHT downstream effect ✅ RESOLVED

**What:** Aung (S3) and one S2 participant both triggered `draft_context_promoted` events while in AI_LIGHT mode.

**Resolution (2026-03-29):** Code inspection confirms promotes in AI_LIGHT are **not** silently discarded. `ChatWindow.tsx` (L336): `shouldForceAgentInvoke = draftContexts.length > 0` — when a promote is active and the user sends any message, the frontend auto-prepends `@agent` and passes the full promoted context metadata (`draftSourceInsightIds`, `draftSourceMessageIds`, `draftContextLabels`) to the backend. The backend treats it as an explicit `@agent` chat request, which IS permitted in AI_LIGHT. S3 AI_LIGHT post-promote event logs confirm `message_sent` (routeMode: `ask`, manual-override) followed all 4 of Aung's promotes.

**Analytical implication:** The S3 AI_LIGHT constraint failure (shortened trip not incorporated) is not explained by promotes being dropped. The context was live input to each agent response. The failure is better attributed to context retention across conversational turns under AI_LIGHT mode. Applies equally to S2 AI_LIGHT (see D2).

### C3 — Facilitator cycled "Quick Start Help" immediately before Shanyl's first messages ✅ RESOLVED

**What:** `user1` cycled the seeded "Quick Start Help" suggestion through `new → accepted → archived → new` at `07:44:37–07:45:24`.

**Resolution (2026-03-29):** Timeline data confirms Shanyl's first message was at **07:50:43** — a 5+ minute gap after the cycling completed. (The `07:44:48` figure from script6 was the session-span start, not first message.) During the cycling window, Shanyl was performing `link_hover` events in the right panel and fired one `focus_insight_from_agent_message` at 07:44:42 (between the first two status changes), confirming the right panel was visible. However: (a) the seed was reset to `new` by 07:45:24 before any participant message was sent; (b) cross-checking `3-cleaned.md` first-impressions notes shows Shanyl's comments were structural — edit context panel, mode clarity, insights discoverability — none referencing a status transition. **Verdict: low-risk confound.** AQ1/AQ2/Q4 responses are not materially contaminated.
